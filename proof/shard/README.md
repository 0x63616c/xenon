# Shard RPC experiment

Run `./scripts/test-shard.sh --proof` from a clean checkout. Rust 1.94.0 and Go 1.27.1 are selected by the committed toolchain files; protoc 36.0 is required and checked. Cargo.lock/go.sum pin dependencies. `scripts/generate-proto.sh` pins both Go protobuf generators; Rust tonic-build generates its bindings from the same committed proto during the build.

The committed `case.json` declares the memory backend, single logical partition, payload/range fixtures, time bounds and fault schedule. The Go test launches a separate Rust process, discovers its dynamically assigned loopback port from readiness, and always kills/reaps it on teardown. It automatically asserts callback laziness, convergent concurrent create, exact blob/encoding, guarded update/assert, typed ownership errors, durable result replay after intervening state, changed-payload rejection, and the declared lost-response fault. A forwarding gRPC server drops the first successfully completed update response; the test asserts the retry used the same ID and applied the operation once.

Rust tests independently reopen SlateDB over the same object store and recover the shard and outcome; they also verify old-owner replay cannot pass a durable fencing barrier and journal capacity fails closed. The node holds a partition gate through durable outcome publication, including logical errors and reads. Transport cancellation leaves admitted work running under that gate until durability settles. Dedup outcomes are retained up to a configured cap; no unsafe expiry is implemented.

Evidence is emitted to `.local/evidence/shard/result.txt` with source commit, clean/dirty state, tool versions, input/lock hashes and automatic results. `--proof` refuses uncommitted input; development runs without that flag remain clearly labeled dirty when applicable. This native bounded experiment will also be composed into the pinned container proof environment; it is not that environment or a full shipping verdict.

## S3 configuration

The Rust node defaults to `XENON_BACKEND=s3`. Set `XENON_BUCKET`, a dedicated nonempty `XENON_PREFIX`, `XENON_PARTITION`, and optional `XENON_LISTEN` (default loopback 7235) / `XENON_MAX_OUTCOMES` (default 10000). Standard `AWS_*` environment supplies credentials, region and optional endpoint. Never commit credentials. The memory backend must be selected explicitly and is used by this fixture only. No bucket is created or deleted by the node.

This slice does not implement directory admission, placement/routing, TLS authentication, other persistence stores, Temporal boot, process-crash S3 recovery, distributed ownership or full schema/version migration. S3 transport is configured but this fixture's results are memory-store evidence, not real-S3 validation. No factory produces placeholder stores. Broader gates remain blocking.

The bounded-progress policy is explicit: at most 64 admitted requests, at most 5 seconds waiting for the partition gate, 20 seconds settling an admitted operation, and a 30-second adapter invocation cap (including transport retries). A storage timeout quarantines the handle before releasing the gate; later operations fail until process replacement/recovery. Tests disable automatic WAL flush to induce real stalled durability and assert quarantine, and inject a hung RPC to assert the client cap. These values are slice defaults, not measured service-level guarantees. Missing-shard Update preserves pinned SQL's typed Unavailable; Assert deliberately implements a real RangeID guard instead of SQL's no-op.
