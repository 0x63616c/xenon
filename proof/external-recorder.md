# External recorder component

Issue #73. This proof-only, opt-in executable is independent of application storage.
Run `python3 scripts/prove.py external-recorder` from a clean checkout for the committed controls. Run `go run ./cmd/xenon-trace-recorder --journal NEW_PATH --capacity 100000` for an explicit loopback server, and `go run ./cmd/xenon-trace-recorder --validate --journal PATH` for offline validation. The controller must launch the recorder in its own process group, preserve its journal, stop producers, close every phase, then SIGTERM the recorder. No runtime controller or adapter hooks are included here.

POST /event accepts strict JSON metadata records: open (phase/status steady or fault), register (phase/producer incarnation/id/sequence/family and optional method/partition/operation_id), terminal (same identity/sequence/phase; status completed with positive local duration_ns or admission_failed with zero duration), death (producer), close (phase). Controller death declarations require independent observed process termination; the recorder itself cannot authenticate that observation. Numeric loopback access is a local trusted proof boundary, not an application endpoint.

A new event is encoded and file Sync completes before acknowledgment. Exact register/terminal retries are idempotent while the phase is open; conflicting reuse rejects. A registration whose ACK is lost may never have executed. Terminal-unobserved registrations have no invented duration. Fault phases can close with unknowns only for declared-dead producers; steady phases cannot. The summary describes registrations, not a census of executed calls. Steady sample eligibility is per observed phase/family and requires 100 completed observations; the future controller must additionally require every mandated family and enforce unchanged latency thresholds. Unknowns and admission failures never enter the completed latency population.

The file is exclusive mode 0600. Admission is bounded to four HTTP handlers, requests to 4096 bytes, IDs to 128 characters, registrations to the declared cap, and journal events to four times that cap. Server read/write deadlines are five seconds. A stalled filesystem Sync cannot be cancelled by Go; the independent controller must impose its external process deadline and classify recorder loss/incomplete journal as measurement failure. There is no fallback to unrecorded work. Flush is local proof-file durability, not Xenon application durability or resistance to whole-host loss. Successful offline validation also requires a canonical footer and closed phases; the controller must check the recorder's successful exit because a close error can occur after footer write.

Controls use actual separate producer/recorder subprocess groups and loopback HTTP, with synthetic work barriers. Discarded ACK, absent END, killed recorder, sequence/capacity errors, and malformed journal all have explicit assertions. This is not runtime measurement, performance evidence, or a full shipping gate. Registration handshake overhead and full helper timing will be wired and tested in the next reviewed slice; no current adapter behavior changes.

Registrations require `measurement` equal to `rpc_invocation` or `execute_attempt`. Attempts additionally require `parent_id` referencing an unterminated invocation from the same producer, phase and family. Invocation registrations cannot have parents. Completed terminal records require a canonical gRPC `result_status` (including OK or Unavailable), separate from terminal observation classification; admission_failed has no RPC result. Summary duration groups encode measurement, phase and family without ambiguous delimiter concatenation. An Execute attempt means the generated unary invocation, including any internal transparent gRPC retries, not individual packets/wire attempts. Exact registration and terminal retries after phase close are permitted without adding journal events; conflicting reuse still rejects.

The integrating controller/client MUST treat every malformed/rejected HTTP event, timeout, or non-204 response as a failed measurement run; it may retry only identical events to reconcile uncertain acknowledgments. This standalone journal cannot attest that a caller obeyed that rule. Offline census validation alone is therefore insufficient for overall measurement PASS: controller protocol-error status and successful recorder exit are also required. Negative protocol controls deliberately submit rejected events and assert rejection; they are not representative success-run telemetry.
