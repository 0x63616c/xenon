# Transaction-safe persistence partitions

Research for [Xenon #2](https://github.com/0x63616c/xenon/issues/2), 5 September 2026. **Proposed placements, not an architecture decision. No runtime or failure tests were executed.**

## Finding

The execution write path has a strong single-history-shard transaction boundary. Matching, task-queue user data, namespace metadata and Nexus endpoints have different boundaries. A partitioned Xenon service is plausible if it routes complete persistence operations into databases that contain their complete transaction domains. Hashing every object, run, task subqueue or endpoint independently would violate inspected contracts.

Two important constraints beyond the initial assessment:

- Both current matching implementations can insert a batch spanning multiple subqueues and lock subqueue zero in the same transaction. The SQL hash includes the subqueue, so copying historical Vitess `range_hash` placement blindly is unsafe without a cross-shard transaction mechanism. See [V1 CreateTasks](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/task_v1.go), [V2 CreateTasks](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/task_v2.go) and [taskQueueIdAndHash](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/task_util.go).
- Nexus endpoint mutation and listing coordinate a shared table version. Per-endpoint independent placement would need additional coordination to reproduce that contract. See [Nexus store](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/nexus_endpoint_store.go).

## Evidence baseline

Temporal is pinned to commit `891d1b648b7252925142cc36f13e40a0e2ed4244`; all Temporal links below use that commit. SlateDB engine observations use release `v0.16.0`. The matrix is a static review of Temporal's low-level interfaces and SQL implementation, not proof of all backend variants or future versions. [Persistence interfaces](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/persistence_interface.go)

A SlateDB transaction is confined to one database. Its serializable-snapshot mode tracks read dependencies, including scan ranges; committing a write returns a handle before object-storage durability. Awaiting that handle and managing one active writer per database are separate requirements from choosing the right partition. [Transactions](https://github.com/slatedb/slatedb/blob/v0.16.0/slatedb/src/db_transaction.rs), [conflict manager](https://github.com/slatedb/slatedb/blob/v0.16.0/slatedb/src/transaction_manager.rs), [writer fencing](https://github.com/slatedb/slatedb/blob/v0.16.0/slatedb/src/fence.rs)

Terminology: a **transaction domain** is the data that must participate together in an operation. A **storage partition** is a movable SlateDB database containing one or more such domains. A **node** can own multiple storage partitions. Moving a partition does not split its transaction domains. These are proposed Xenon terms.

## Cross-partition reads are distinct from cross-partition writes

The following operations need distributed enumeration if their data domains are split across databases:

- **GetAllHistoryTreeBranches:** spans history shards. SQL continuation includes (ShardID, TreeID, BranchID). The interface explicitly permits skips/duplicates under concurrent branch creation/deletion, so this is not a requirement for a globally consistent snapshot. [History store](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/history_store.go), [interface](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/persistence_interface.go)
- **ListTaskQueue:** traverses matching hash ranges with a continuation token. Xenon must enumerate all matching domains without losing cursor progress during ownership movement. The existing SQL scan-partition helper is not the Xenon ownership directory. [Task queues](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/task_queues.go), [hash helpers](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/task_util.go)
- **QueueV2 ListQueues:** lists metadata and derives counts/last IDs. Splitting named queues requires aggregation and stable page interpretation, not a transaction spanning all queues. [QueueV2](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/queue_v2.go)
- **Visibility:** execution commits a visibility task, then asynchronous processing updates the separate visibility store. No execution/document cross-store transaction is required by that path. Partitioned visibility still needs its own query, ordering/count and page-token design; this note does not choose that layout. [Visibility executor](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/service/history/visibility_queue_task_executor.go)
- **ListConcreteExecutions:** the inspected SQL store explicitly returns Unimplemented. Therefore “match SQL” and “implement every persistence method meaningfully” are different targets; compatibility scope must be decided explicitly. [Execution](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/execution.go)

## Conditions must survive the gRPC boundary

One complete persistence operation should be the unit of routing and execution in the candidate service, rather than exposing remote Get/Put calls and attempting client-side transactions. This is a design inference from the transaction scopes above, not an approved RPC design.

The SQL helper checks the stored DBRecordVersion against **requested version minus one** when the requested version is nonzero; legacy zero-version handling compares NextEventID instead. A simplistic equality check would be wrong. WorkflowConditionFailedError includes observed NextEventID and DBRecordVersion; current-workflow conflicts carry current-run details. ShardOwnershipLostError is different again. These structured values cannot be flattened into generic gRPC Internal errors without affecting Temporal's handling. [Version and current-run helpers](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/execution_util.go)

An engine transaction conflict is also not automatically a Temporal condition failure: the backend may need to retry and reevaluate the requested condition. Conversely, an RPC timeout after durable commit is ambiguous, not proof of rollback. Queue enqueue APIs that allocate IDs especially need caller-level retry review. These are unresolved adapter contracts, not reasons to weaken durability.

## What the Vitess precedent proves

PlanetScale's December 2022 first-party account describes a customer running sharded Temporal in production. Its example uses shard_id for major execution/history tables and range_hash for matching, alongside an unsharded keyspace. Some mutable-state tables were left unsharded, so the example does not establish that every transaction stayed within one physical database. It does not specify enough transactional configuration to infer that.

The example predates the current code and does not demonstrate current fairness, multi-queue user-data, CHASM, Nexus or visibility compatibility. It is useful evidence that a database routing layer can sit behind Temporal, not proof that its exact layout transfers to SlateDB. [PlanetScale production account](https://planetscale.com/blog/temporal-workflows-at-scale-sharding-in-production)

Current Temporal config explicitly calls TaskScanPartitions experimental and explains its use for Vitess scan efficiency. Its implementation partitions ListTaskQueue scans by hash ranges; it is not a general persistence-router or dynamic ownership mechanism. [Configuration](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/config/config.go), [scan implementation](https://github.com/temporalio/temporal/blob/891d1b648b7252925142cc36f13e40a0e2ed4244/common/persistence/sql/task_queues.go)

## Candidate colocations for the decision ticket

These are options for Calum's review, not decisions:

1. **History:** assign whole history shards to SlateDB partitions; one database can contain multiple history shards. Include shard rows, all execution maps, all runs, history branches and history task categories.
2. **Matching:** partition by namespace/task-queue/type while colocating every subqueue and its ownership metadata. Distinguish ordinary/fair storage representations.
3. **Task-queue user data:** partition by namespace, keeping every queue's user data and build-ID reverse mapping for that namespace together. This preserves arbitrary current request batches but limits one namespace's metadata write scale.
4. **Global domains:** keep namespace catalog/notification version and Nexus catalog/table version in appropriately sized shared domains. They may be separate databases or share a database; the observed contracts do not require joining them to each other.
5. **Other domains:** cluster metadata/membership and named generic queues can have their own placements. Favor coarser placement until global enumeration and ownership tests justify finer granularity.
6. **Visibility:** make its placement decision separately after query/ordering research.

This layout could scale by redistributing whole databases over more nodes. It does not establish unlimited scale: one hot indivisible transaction domain remains bounded by one writer. Splitting that domain would require a different contract-preserving design.

## Remaining evidence gaps and validation targets

The operation-family matrix is concrete but **not an exhaustive error/predicate conformance specification**. Before closing implementation scope:

- Audit SQL plugin predicates, affected-row behavior, transaction wrappers and upstream tests method by method. This note identifies important typed conditions and known wrapping asymmetries; it does not claim every malformed-input/error branch is covered.
- Trace all manager/caller transformations, especially matching task-queue naming, batch formation, queue retry handling, replication/reset and CHASM. Confirm every request carries the routing keys the RPC adapter needs.
- Confirm whether the chosen released Temporal baseline differs from this pinned main commit. Do not silently advertise main-branch findings as a tested release.
- Run upstream persistence tests against candidate transaction domains. Include a two-subqueue CreateTasks batch, stale subqueue-zero RangeID, two-queue user-data update with one conflicting version, Nexus page version changes, and namespace rename conflicts.
- Test state-plus-tasks and related-run atomicity, history append preceding a failed state commit, branch deletion across ancestor ranges, and read behavior around pending durability.
- Test partition handover while all relevant writes and enumerations run. A placement matrix does not prove writer fencing, routing freshness, durability acknowledgements or ambiguous RPC retry behavior.
- Measure hot namespace/global metadata domains and fair matching hot queues before deciding that these placements meet the desired operating envelope.

**Conclusion:** the source supports multiple transaction domains that can be assigned to separate SlateDB databases. It does not support one universal ShardID router or arbitrary per-key sharding. The strongest next decision is which of the candidate domains Xenon will implement and validate first, with dynamic ownership tested from the outset.
